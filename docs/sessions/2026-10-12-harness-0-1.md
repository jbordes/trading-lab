# Bitácora — Implementación del Harness 0.1

**Fecha:** 2026-10-12

**Estado:** Cerrada

**Objetivo:** analizar el harness utilizado en otros proyectos y construir una base portable, segura y verificable antes de implementar herramientas del dominio de TradingLab.

**Schema de sesión:** session-v1

## Hechos y evidencias

- TradingLab se encontraba en fase documental, sin harness ni código de aplicación.
- La VPS dispone de Python mediante el launcher `py`, pero inicialmente no tenía uv ni el alias `python` en `PATH`.
- Los tres documentos usados como referencia pertenecen a Fenix y a una configuración global personal; permanecen fuera de Git.
- La arquitectura exige separar Git, catálogo, storage y bitácora, además de conservar decisiones durables mediante ADR.

## Interpretaciones

- Copiar el harness de Fenix habría introducido dependencias y procedimientos ajenos a TradingLab.
- Un núcleo en PowerShell habría dificultado el trabajo ocasional desde macOS y Linux.
- Las validaciones masivas de artefactos no deben ejecutarse durante cada sesión porque el workspace histórico supera ampliamente el volumen apropiado para un preflight.

## Trabajo realizado

- Se creó un núcleo portable en Python administrado con uv.
- Se agregaron validaciones rápidas y completas, tests, CI multiplataforma, plantilla de PR y reglas operativas.
- Se agregó el proceso versionado de sesiones, su generador, validación estructural y control de trazabilidad por rama.
- Se creó la estructura de ADR y el primer ADR del proyecto.
- Se documentaron los elementos de la arquitectura cubiertos por el harness y los postergados hasta que exista el flujo piloto.

## Decisiones

- Adoptar Python 3.14 y uv para la lógica portable del harness.
- Usar ramas cortas, PR, CI de solo lectura y merge humano.
- Exigir una entrada de sesión cerrada por rama antes del merge.
- Mantener humana la redacción de hechos, interpretaciones y decisiones; los scripts solo crean y validan la estructura.
- Registrar decisiones durables en ADR sin convertir la bitácora en una segunda base de datos.

## Validación

- `uv run python scripts/check.py full` ejecutado localmente en Windows.
- Compilación de los scripts mediante `python -m compileall`.
- Revisión del diff preparado y comprobación de whitespace mediante `git diff --cached --check`.
- La matriz de CI en Windows, macOS y Linux se ejecutará al abrir el pull request.

- Definir backup y restauración de `_storage/` cuando se seleccione su ubicación autoritativa.
- Elegir la estrategia real que servirá como piloto vertical.
