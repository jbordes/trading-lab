## Interpretaciones

- La bitácora debe representar el trabajo del día aunque no haya cambios de código, estrategias o datos versionados.
- Acoplarla a una feature produciría una historia incompleta y conflictos innecesarios al integrar ramas.

## Decisiones

- Las features se desarrollan en ramas y se integran mediante pull request con merge humano.
- Las bitácoras diarias son canónicas en `main` y se publican mediante commits exclusivos.
- Solo se pueden crear o actualizar entradas cuya fecha inicial corresponda al día actual en `Europe/Madrid`.
- Las entradas de días anteriores son inmutables; cualquier corrección posterior se registra en el día corriente.
- El archivo normal de cada jornada es `YYYY-MM-DD.md` y reúne todos sus temas mediante bloques horarios o subtítulos.
- El sufijo `-tema` solo se admite cuando exista una razón excepcional para dividir deliberadamente la jornada.
- Los scripts serán entradas delgadas; la lógica reutilizable vivirá en `src/tradinglab/` cuando aparezca el primer componente real.
- La arquitectura limpia se aplicará proporcionalmente al problema, sin imponer abstracciones o infraestructura sin una necesidad concreta.
- Excel será la primera proyección del pipeline, no su fuente de verdad; la captura y normalización quedarán desacopladas para admitir una base futura.
- La API MT5 se usará solo en modo lectura y se conservará un adaptador de reporte para backfill y reconciliación.
- Antes de implementar se validará con el socio el contrato del informe, la identidad de estrategia y el corte diario.
- El entregable v1 será un workbook por combinación autorizada de estrategia y Magic Number; el master queda fuera de alcance.
- `magic_number` se incorporará después de `strategy_id` como columna obligatoria y filtrable.
- La identidad técnica conservará cuenta y Magic Number para evitar mezclas si un número se reutiliza en otro entorno.
