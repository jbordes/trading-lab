## Interpretaciones

- El piloto no necesita todavía un modelo canónico amplio ni una base productiva; utiliza un snapshot mínimo y memoria acotada.
- Una consulta diaria de la API no garantiza reconstruir todos los cambios intradiarios; primero debe medirse esta limitación en el spike antes de justificar un colector MQL5.
- Las métricas históricas necesitarán persistencia, pero su frecuencia y esquema deben derivarse de las fórmulas aprobadas por el socio.
- El detalle por operación es una base más útil que una agrupación temprana por bot; la agrupación podrá derivarse posteriormente mediante Magic Number.
- Una ventana incremental necesita reconciliación periódica porque la documentación de MT5 no define con precisión todos los casos temporales de las órdenes históricas.

## Decisiones

- La decisión anterior de producir Excel como entregable v1 quedó reemplazada; Excel podrá ser una exportación futura.
- El registro de bots debe relacionar Magic Number, bot, ID SQX, estrategia, cuentas y vigencia.
- Las observaciones serán inmutables y las correcciones posteriores se registrarán como revisiones enlazadas.
- El master histórico no será un entregable de la v1.
- Las tecnologías futuras se elegirán por adecuación, mantenibilidad y evidencia del piloto; no se impondrá Python cuando otra opción sea mejor.
- El primer dashboard se ejecuta solo en `127.0.0.1`, usa MT5 en modo lectura y comienza con cuenta demo.
- No se implementan fórmulas sugeridas por Gemini; las definiciones serán provistas y aprobadas por el socio.
- Apache ECharts queda diferido hasta necesitar distribuciones, matrices de covarianza y gráficos combinados; el primer corte usa SVG local sin dependencias remotas.
- El primer muestreo muestra operaciones individuales y filtra por Magic Number; no persiste historial operativo ni presupone todavía una entidad canónica de bot.
- La actividad reciente continúa siendo estado reconstruible en memoria; no justifica por sí sola adelantar SQLite ni el modelo histórico de riesgo.
