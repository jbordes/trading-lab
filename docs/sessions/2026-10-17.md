## Interpretaciones

- La API Python puede aislar varias terminales solo con una topología adicional:
  un worker/proceso por terminal, ruta explícita, validación continua de ruta de
  datos/cuenta/servidor y supervisión de cada proceso. No debe compartirse el
  módulo MT5 entre fuentes concurrentes ni utilizar descubrimiento automático.
- Ese aislamiento es viable, pero replica responsabilidades de configuración,
  identidad, salud y ciclo de vida que el collector resuelve naturalmente dentro
  de cada terminal. La evidencia permite decidir ya la topología: collector como
  fuente operativa primaria y Python como diagnóstico o reconciliación aislada.
  Aun así, falta una validación acotada de campos y operaciones reales; serviría
  para comprobar corrección del contrato, no para volver a decidir la topología.

- Una integración que pueda confundir terminales no es apta como fuente del
  dashboard en una VPS con varias instancias MT5. Para conservar la API Python,
  deberá demostrarse que cada proceso puede vincularse y verificarse contra una
  ruta de terminal, carpeta de datos, cuenta y servidor esperados; de lo contrario,
  quedará descartada para este caso y el collector por terminal gana prioridad.

- El recorrido MQL5 hacia el dashboard ya quedó demostrado en una cuenta demo
  vacía. Aún falta compararlo con la API Python cuando haya operaciones reales;
  este piloto valida transporte y recuperación, no decide por sí solo qué vía
  será la fuente definitiva.

- La lógica determinista de cola, reintentos, descartes y validaciones quedó
  comprobada dentro del runtime MQL5. Esto no demuestra todavía el flujo real
  del collector ni su equivalencia con la captura mediante la API Python.

## Decisiones

- Se aceptó adoptar un collector MQL5 por terminal como fuente operativa primaria.
  La API Python queda como herramienta auxiliar de diagnóstico o reconciliación:
  una terminal por proceso, ruta explícita y validación de identidad. La comparación
  amplia deja de ser un gate de topología; permanece una validación acotada del
  contrato del collector con operaciones reales.
- La decisión durable se formalizó en ADR-0004 y se abrió el PR #9 para alinear
  arquitectura, roadmap, documentación operativa y README. No se modificó código;
  el merge continúa a cargo de una persona.

- Corregir la respuesta del receptor en vez de relajar las confirmaciones del
  collector: una muestra solo sale de la cola cuando MT5 reconoce el HTTP esperado.

- Mantener pendientes y separados el piloto demo integrado y la comparación
  MQL5-versus-Python; no promover aún el collector a solución definitiva.

- La web se organiza en página de proyecto (`/`) y panel (`/dashboard`) con tema
  dual, y la salud de la fuente viaja como campo aditivo `source_health` en
  `/api/state`. La decisión durable se documentó en ADR-0005 (estado `proposed`).
